Native apps, written in Eskiu

Write the interface once as Eskiu functions. It draws UIKit views on iOS, android.view views on Android and the DOM on the web, from the same code.

Get started View on GitHub

Create native apps for Android, iOS and the web

A component is an ordinary Eskiu function. It calls Column, Text and Button to build the view, and keeps its state in signals. The app compiles to machine code on iOS and Android and to WebAssembly on the web.

Text, buttons, fields, switches, lists, modals and alerts are the platform's own controls, with the platform's accessibility. 

import <string>;
import <ui>;

void Counter() {
    Column(Style{padding: 24, gap: 12}) {
        *Signal<int> count = use_signal<int>(0);
        String label;
        defer String_free(&label);
        String_format(&label, "Pressed %d times", count.get());
        TextWith(Style{font_size: 28, font_weight: 700}, label.data);
        Button("Press me") {
            count.set(count.get() + 1);
        }
    }
}

Written in Eskiu, drawn by the platform

Components, state and layout rules are the same Eskiu code everywhere. Each frame, the core sends the platform one buffer with the changes, and a thin host applies it to real views laid out by Yoga, the engine React Native uses.

iOSUIKit, from Objective-C++
Androidandroid.view, from Java and JNI
WebThe DOM, from WebAssembly
macOSThe web host in a WKWebView window

Updates that touch only what changed

A block records the signals it reads. When one changes, only that block runs again and its children are matched by key, so a list keeps each row's state when it is reordered. Virtual lists mount only the rows near the viewport, so a million rows cost what a screenful does.

Hooks, keys and memos are checked as the app runs, and a mistake stops with where it happened: in Column[0] > TodoRow[key 3].

See each change in a third of a second

ui serve watches the app and the packages it depends on, and builds again when a file changes. On the web the page reloads, keeping its URL and its saved data. On the simulator and on Android the running app starts again on the new code in the same process, so nothing is installed or launched again.

A build that fails shows the compiler's errors over the app until the next one works.

Overlays, pickers and toasts

<ui/kit> is a set of themed components built from the same elements: cards, buttons, fields, checkboxes, tabs and bars, and the things that open over the content. A Popover places itself next to what opened it, above or below, inside the window. DatePicker, Select, DropdownMenu, ColorPicker and Tooltip are built on it, and kit_toast shows a message for a few seconds.

The theme follows the system's light or dark appearance, or one you set.

Motion and gestures

A style can move, scale and turn an element and fade it, and transition_ms animates each change on the platform: UIKit animations, Android's view animator and CSS transitions. A spring is one of the curves.

ui_on_pan reports a drag with its distance and speed, and takes over from a button inside once the finger moves. use_animated moves a number to its new value, for what the platform cannot animate. The kit's SwipeToDelete is built from the two. 

*Signal<int> dx = use_signal<int>(0);
*Signal<bool> held = use_signal<bool>(false);
ui_on_pan(void(Pan p) {
    held.set(p.phase == PanBegan || p.phase == PanMoved);
    dx.set(held.get() ? p.dx : 0);
});
Row(Style{translate_x: dx.get(),
          transition_ms: held.get() ? 0 : 250,
          easing: EaseSpring}) {
    Text("Drag me");
}

The phone's services, from one API

What an app asks of the system has one name on every platform, and each host answers with the platform's own service.

Light and darkui_color_scheme() and the kit's themes follow the system as it changes.
AccessibilityLabels for VoiceOver, TalkBack and screen readers, the text size, reduced motion and announcements.
LanguageThe user's locale and whether it reads right to left.
Networkui_fetch through NSURLSession, HttpURLConnection and the browser's fetch.
Saved dataSmall values that outlive the app, and a data directory for files.
Share and clipboardThe system's share sheet, copy and paste.
HapticsSelection, impact and notification feedback, a vibration on the web.
Timersuse_interval and use_timeout, kept by the platform's clock.
Keyboard and insetsThe safe area and the keyboard, or the whole screen edge to edge.

Screens on the phone, pages on the web

A router holds a stack of routes and a navigator draws it. On iOS and Android each route is a screen that slides in, with the back button and the edge swipe. On the web each route is a URL, and the browser's back and forward buttons move the app. Deep links open their screen on all three.

The screens under the top stay mounted, so going back finds them as they were.

In a wide window, a tablet or a browser on a computer, the kit's text and controls get denser and the starter moves its tabs to a sidebar, so the web build reads as a web app and the phone keeps its own layout. 

Navigator(router, void(string route) {
    string id = route_param("/places/:id", route, 0);
    if (id != null) { PlacePage(router, atoi(id)); }
    else { PlaceList(router); }
});

// elsewhere
router.push("/places/2");
router.back();

Native code when you need it

An app or a package ships code per platform in native/: Objective-C or Swift on iOS, Java, Kotlin or C on Android, JavaScript on the web. Eskiu calls it through extern functions, it answers with events, and it can register its own views for NativeView.

Third-party libraries come from ui.toml: Maven dependencies build through Gradle and Swift packages through Xcode, and a package brings its own to every app that uses it. 

# ui.toml
[app]
name = "Explore"
scheme = "places"

[ios.spm]
Collections = { url = "https://github.com/apple/swift-collections", from = "1.1.0" }

[android]
dependencies = ["com.google.android.material:material:1.12.0"]
permissions = ["android.permission.CAMERA"]

From your editor to the stores

ui open ios and ui open android make the app's Xcode and Android Studio projects and open them there. Each Run builds the Eskiu code first, so an edit to a .esk file is in the next Run, with the native debugger, the profilers and your own phone.

ui release builds for the App Store and Google Play: an IPA signed for your team, and an App Bundle signed with an upload key it makes and keeps for you. It checks the icon and the app's id before building, takes the build number from the clock, and with --upload sends the iOS build to TestFlight. 

# ui.toml
[app]
name = "Explore"
id = "com.yourcompany.explore"
icon = "icon.png"
version = "1.0.0"

# Xcode, with each Run building the Eskiu code
$ ui open ios

# the App Store and Google Play
$ ui release
ios: build/ui/ios/release/Explore.ipa
android: build/ui/android/release/Explore.aab

From nothing to a running app

The ui tool makes a project and builds or runs it on each platform. It needs emscripten for the web, Xcode for iOS and the Android SDK for Android.

Every element, hook and service is listed in Components and APIs.

To start from a whole app, ui-starter has tabs, screens with links, a list from the network and a saved theme. For a package with native code, start from ui-package-template. 

git clone https://github.com/eskiu-lang/ui
eskiuc ui/tools/ui/main.esk -o ~/.eskiu/bin/ui

ui new myapp && cd myapp
ui serve          # or ui serve ios, android, macos

ui is in preview. Views are written with trailing blocks: Column(Style{padding: 16}) { ... } passes the block as the call's last argument. Windows and Linux hosts come later.
